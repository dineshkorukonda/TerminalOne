# Windows profiling

Issue #43 uses npm run test:profile after native:build and build in an interactive Windows environment. The harness runs real ConPTY with the built application under Playwright, records CPU model/logical cores/system memory, OS/build, architecture and runtime versions, and writes test-results/performance/baseline.json.

The workload records one fresh-profile and two same-profile startup samples, 1 MiB of synthetic ASCII payload rendered through xterm, a three-pane snapshot and 20 native session create/close cycles. Each closed shell is checked through a retained process handle. Timings include automation and command submission; they are not isolated terminal-engine throughput or cold OS-cache measurements. Aggregate working set and CPU scope is Electron processes from app.getAppMetrics, excluding external shells, helper and conhost. This is not a claim about total system memory or absence of all leaks. Installed-app smoke separately records one actual packaged launch sample without debugging instrumentation.

The harness also records a ten-second idle snapshot, three native window resize completion samples, and Electron working-set samples after each create/close cycle. Resize timings measure window geometry visibility through automation; existing native workspace tests separately verify PTY resizing. No numeric Windows baseline is invented here; actual CI artifacts must supply it. Compare repeated runs on the same recorded machine class and review process exit failures and memory drift before making performance claims. A longer soak and external-process profiling remain useful follow-up evidence.

Proposed review budgets, pending owner agreement after measurements: investigate regressions above 20% in median same-profile startup or output completion on comparable hardware; investigate monotonic Electron working-set growth over repeated equal workloads rather than a single transient allocation. Any surviving owned shell is a hard failure. Existing queue/session/scrollback limits remain hard resource bounds. These are proposed review rules, not agreed release budgets or measured achievements. Record accepted numeric budgets and supporting measurements in the release qualification review before closing #43.
