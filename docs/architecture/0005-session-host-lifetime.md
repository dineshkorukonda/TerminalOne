# Decision 0005: one utility-process lifetime per terminal session

The node-pty 1.1.0 dependency can retain ConPTY worker/native resources after a shell exits. Successful profile run 39102983220 showed one utility process (PID 7596 in that run) rising from 96,172 KiB to 278,228 KiB across the workload, with 275,448 KiB still resident after ten seconds idle. These are Windows Server observations, not a universal memory budget. The other utility stayed near 43 MiB. The profile did not record service names, so identifying the growing process as the PTY host is an inference from its growth pattern and dependency source, not an explicit label in that JSON. The source's natural-exit cleanup destroys its output socket without disposing its conout worker; upstream tracks related lifecycle leaks in [node-pty #965](https://github.com/microsoft/node-pty/issues/965) and [#887](https://github.com/microsoft/node-pty/issues/887).

Main now composes SessionPtyPort around a factory for UtilityPtyPort. Each terminal gets its own utility process and existing Job Object helper. Closing a session shuts down that host and waits for its retained UtilityProcess exit event; natural exit retires it after final output acknowledgments. Process exit releases that session's worker isolates and native resources. No private dependency methods are patched, and node-pty's unsafe bare-PID kill fallback remains unused. Existing Job Object ownership of shell descendants is preserved.

Allocation counts both live and retiring hosts against a sixteen-host adapter bound; application limits still allow four visible sessions per owner. Disposal is idempotent, startup/disposal races retire the allocated host, late acknowledgments cannot restart a host, and an unconfirmed shutdown blocks further allocation. The existing fail-closed whole-port failure notification and subsequent fresh-session recovery remain in place for ordinary host crashes.

The tradeoff is an extra utility/helper process for each simultaneous pane and fresh utility startup for every session. Existing profiles now record process names and service identifiers and assert that twenty create/close cycles return to the original live pane's host PID set. Per-process, settled-memory and timing measurements remain mandatory on Windows CI before claiming a memory improvement. Renderer/GPU retention and long-running workloads still need measurement; process isolation alone is not proof of complete leak freedom. No performance budget or release approval is implied.

Electron documents that the fork option serviceName appears in ProcessMetric.name; host lifecycle assertions use that name, not the separate internal serviceName field. See [utilityProcess.fork](https://www.electronjs.org/docs/latest/api/utility-process#utilityprocessforkmodulepath-args-options).
