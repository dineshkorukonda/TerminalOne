# Conservative shell adapter boundary

Issues #24 and #25 establish this boundary; recognizers, resolution, state and compatibility checks are delivered in #26–#32. The contracts live in `src/domain/shell-adapter/contracts.ts` and have no transport or platform dependencies.

Analysis is an explicit operation on a complete command string. It is never reconstructed from terminal keystrokes, pasted into another runtime automatically, or used as a script translator. Recognition reports positive syntax evidence, confidence represented by recognized/unknown/ambiguous, and a reason code. It does not assert what an alias, function, executable, pipeline or arbitrary script will do. Unknown and conflicting evidence preserve the exact string in the active shell.

An adapter registry combines narrow PowerShell, CMD and Bash recognizers. Quoted content is not command evidence; incomplete quoting, operators, multiline input, function definitions, scripts, interpolation and unsupported forms are conservative fallbacks. Recognition can identify a syntax family without guaranteeing execution semantics: aliases/functions remain context owned by the current shell. No allowlist is a command safety classifier.

Resolution is separate from recognition. The active shell remains the default, including interactive programs and unknown input. A recognized incompatible form produces a deliberate-selection strategy; it never silently starts a different shell. Missing optional executables are unavailable, not downloaded. Discovery resolves executable paths and fixed startup argument arrays in infrastructure. Shell capability metadata contains no executable supplied by the renderer.

Each native session owns its working directory, environment, aliases, functions and interactive process. An explicit shell-integration producer may report monotonically sequenced prompt boundaries, Windows drive/UNC/Unicode cwd, environment revision and exit status. The application state tracker accepts only its configured producer/session, and stores no environment values. Until a trusted producer reports, state is unobserved and routing falls back to the active shell. Failure invalidates the observation. State is never copied between sessions or shell families. This phase does not install prompt hooks or infer state by scraping terminal output.

A new shell retains its startup cwd/environment; selecting another runtime would lose state unless a later explicit workflow documents and confirms that transition. No automatic migration is implemented. Signals and stdin stay on the existing PTY: Ctrl+C remains raw input, exit status comes from that session, and interactive processes stay attached. Execution strategies are decisions for an explicit consumer, not permission to execute or a new generic process/IPC API.

Representative decisions: `dir` is unknown; `Get-ChildItem` is narrow PowerShell evidence; `dir /b` is narrow CMD evidence; `export NAME=value` is Bash stateful evidence. Quoted mentions, pipelines, `cd`, functions, mixed operators and incomplete input stay unchanged. The Windows compatibility fixture executes only synthetic cases directly in detected shells, recording availability, cwd/environment isolation, quoting/pipelines, exit codes, signals and tree cleanup. Unit tests cannot stand in for native Windows execution.
