# Decision 0003: developer data and explicit assistance

Phase 4 persists validated, versioned local preferences separately from opt-in command history. Main owns bounded files under userData/developer-data, atomic writes and scoped file/folder dialogs. Corrupt settings are preserved and require an explicit reset. Version 1 is the initial format; unsupported versions fail before mutation. Export includes theme, shortcuts, project folder paths and saved launch layout. It excludes history, environment variables, terminal output and live process identifiers.

Project folders must be absolute normal Windows/UNC paths and exist when launched. Restoration is offered explicitly and creates fresh processes from approved launch metadata; it never replays commands or copies a live session's environment. It restores launch folders, not later changes made by cd. Missing projects/shells fail visibly. Four panes remain the application limit.

History is off by default. Newly integrated Windows PowerShell/PowerShell 7 sessions capture complete commands through PSReadLine's AddToHistoryHandler, not raw input events or terminal-output scraping. Native PSReadLine persistence is disabled in these integrated sessions. Per-session random frame identities and bounded parsing keep metadata out of xterm, and main checks current opt-in and private-session policy before saving. These same-user processes are not a security sandbox: commands can inspect/alter their own integration. Data from the hook is history, never an execution authorization or trusted prompt state observation. CMD/Git Bash retain native behavior and do not capture app history. Their own shell histories are outside app retention controls.

Private history integration is supported only for PowerShell. Private sessions install the no-save policy but never reach the app history sink. History retention is bounded, clearing/disable removes app records, leading-space commands and common credential terms are excluded. This filter cannot identify every secret: users must use a private tab or disable capture before sensitive commands. Opt-in history is plaintext local data, not a credential vault, and is excluded from settings export.

Suggestions come from the same-shell local history and fill an explicit command draft. Accepting a suggestion never writes to a PTY or executes a command. Users review/copy the draft and retain native terminal completion and interactive-program behavior. Stale searches are canceled at the presentation boundary. Clearing history invalidates both search and suggestion requests before invoking the capability, suspends lookups while clearing, and preserves the command draft. A failed clear remains visible and can be retried; fresh searches resume after the operation settles.

The optional explanation surface is disabled by default and provides a small static offline reference only after explicit opt-in. It has no model provider, telemetry, network client or execution path. Any future external provider requires a separate reviewed implementation with disclosure, per-submission consent, secret policy, provider isolation and tests. This local surface does not claim semantic parsing or a command safety assessment. Security review remains part of Phase 5 before beta qualification.
