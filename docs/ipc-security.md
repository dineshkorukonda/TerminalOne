# Desktop capability boundary

The sandboxed preload exposes named capabilities on `window.desktop`: `getAppInfo`, `openExternal`, `listShells`, `createSession`, `writeSession`, `resizeSession`, `closeSession`, `acknowledgeSession`, and `onSessionEvent`. The event subscription returns an idempotent unsubscribe function and strips Electron's event object. There is no generic invoke/send method, channel selection, Node module, or filesystem API. The only external URL allowed is `https://github.com/dineshkorukonda/TerminalOne`, compared exactly before calling Electron's shell API. Terminal output cannot open links automatically.

The renderer requests a detected shell ID and bounded integer grid. Main resolves the executable, fixed argument array, and home directory; the renderer cannot supply executable paths, command-line arguments, environment, or working directory. Session IDs belong to the requesting webContents. Write, resize, acknowledge, and close reject unknown/unowned IDs. Input is preserved verbatim, limited to 16,384 characters per call; native output is chunked, acknowledged after xterm parses it, and bounded to 256 KiB per session. Resizes are coalesced; native requests and session counts are bounded. Raw terminal input/output is never logged or persisted by the app.

`node-pty` loads only in an Electron utility process. A compiled Windows helper owns each shell in a Job Object with kill-on-close, watching retained main/utility process handles. Session close, natural exit, window loss, renderer loss, normal quit, and utility failure terminate owned trees. These are same-user shell processes with the user's existing privileges; the Job Object is a lifecycle boundary, not a security sandbox for malicious commands or processes launched through external services.

The main process authorizes every request against the exact window's webContents, its current main frame, and its configured document URL. Other windows, subframes, missing frames, and other documents fail. It then checks the complete argument list and payload before returning data or opening a URL. Closing the window removes its handlers.

`src/contracts/` contains inert capability types and internal channel constants, with no framework imports. Preload, renderer, and infrastructure may depend on these contracts. Domain/application layers do not depend on transport contracts. New capabilities require a typed contract, validation, sender authorization, and negative tests; never expose generic IPC.

Windows enable sandboxing/context isolation and disable Node integration and webviews. All renderer/frame navigation, redirects, popups, and permissions are denied. External links use the allowlisted capability. Packaged windows disable DevTools; packaged startup rejects inspector/remote-debugging switches and `NODE_OPTIONS`. The application never enables debugging on its own. Packaging/fuse verification remains part of #40 and the security audit in #44; development launch tests use Playwright instrumentation and are not proof about a packaged binary.

The built HTML's CSP permits local scripts/styles only, with no inline scripts, eval, remote connections, objects, or form submissions. Vite development uses only `http://127.0.0.1:5173/`, adding the inline React Refresh preamble, inline styles, and local WebSocket needed by HMR.

Run `npm run test:unit` for schemas, authorization, startup flag policy, and architecture checks, then `npm run test:smoke` for the actual bridge, invalid payload rejection, untrusted-window rejection, navigation/popups, CSP, and Node isolation. A startup probe simulates the packaged flag in the real Electron process and verifies debugging options cause immediate exit, rather than an unhandled-error dialog. This is not a packaged distribution/fuse test. Linux tests need a display and Electron system libraries. Windows CI runs smoke and native integration separately. No packaged installer, OS sandbox enforcement, or real Windows result is claimed by Linux testing.

References: [Electron security](https://www.electronjs.org/docs/latest/tutorial/security/) and [IPC](https://www.electronjs.org/docs/latest/tutorial/ipc).
